## 1. 背景与阶段定义

MindSurf Voice AI 的最终目标是实现支持实时语音输入、文本/语音双模态输出的桌面语音 AI。最终形态会将音频编码为离散 token，并由多模态 LLM 原生理解和生成音频。

第一阶段不等待原生音频模型成熟，采用以下级联链路验证产品闭环：

```text
全局快捷键
  → 麦克风采集
  → PCM 音频流
  → ASR
  → LLM
  → 文本结果
  → TTS
  → 流式语音播放
```

客户端使用 Tauri 2、Vue 3 和 TypeScript；推理服务通过 WebSocket 与客户端长连接。第一阶段形成的录音、连接、状态管理和播放模块应能在后续替换为原生音频 token 链路，而不重写整个客户端。

## 2. 阶段目标

第一阶段必须完成以下核心闭环：

1. 用户通过全局快捷键开始和结束录音。
2. 客户端采集单声道语音并流式发送给服务端。
3. 服务端完成 ASR、LLM 和 TTS 级联推理。
4. 客户端实时显示识别文本和 AI 回复。
5. 用户可将识别文本或 AI 回复注入当前应用的光标位置。
6. 客户端收到首个语音分片后立即开始播放，不等待完整音频生成。
7. 用户可以中断当前录音、推理或语音播放。
8. 断线、权限拒绝和服务不可用时，客户端给出可理解且可恢复的提示。

阶段 KPI：

| 指标                             |               目标 |
| -------------------------------- | -----------------: |
| 用户说完到出现最终识别文本       |           ≤ 1.5 秒 |
| 用户说完到出现首个回复文本 token |             ≤ 2 秒 |
| 用户说完到开始播放回复语音       |             < 3 秒 |
| 本地网络下音频上行丢帧率         |             < 0.1% |
| 连续完成 20 轮语音请求           | 无崩溃、无状态卡死 |
| 空闲状态 CPU 占用                |               < 2% |

延迟指标以本地 RTX 4090 推理服务、普通话短句、稳定局域网或 localhost 环境为基准。性能测试必须记录音频时长、模型配置、硬件和各阶段耗时，避免只记录总耗时。

## 3. 非目标

以下能力不属于第一阶段的强制交付范围：

- 原生音频 token 输入或输出。
- 全双工持续对话。
- 多人说话分离。
- 音色克隆和自定义声音训练。
- 情绪 token 控制。
- 复杂 Agent、工具调用和长期记忆。
- 云端账户、支付和多租户系统。
- 完整的移动端适配。
- 自研 ASR、TTS 或声码器。

第一阶段可以为这些能力预留接口，但不能让它们阻塞核心闭环。

## 4. 用户交互

### 4.1 默认交互流程

1. 应用启动后常驻系统托盘，并尝试连接推理服务。
2. 用户在任意应用中按住录音快捷键。
3. 客户端播放轻提示音并显示录音悬浮窗。
4. 用户说话时，悬浮窗显示音量和录音时长。
5. 用户松开快捷键，客户端结束音频流并进入识别状态。
6. 服务端返回 ASR 文本，客户端在悬浮窗中显示。
7. 听写模式按设置自动将 ASR 文本注入当前前台窗口；助手或混合模式继续等待 LLM。
8. 助手或混合模式下，服务端流式返回 LLM 文本，并按请求配置返回 TTS 音频；客户端边接收边展示或播放。
9. 根据当前模式和用户设置，通过 Windows 原生键盘输入事件将 ASR 文本或 AI 回复注入当前前台窗口。
10. 任务结束后悬浮窗自动收起，应用继续在托盘运行。

### 4.2 默认快捷键

| 操作         | Windows        |
| ------------ | -------------- |
| 按住说话     | `Ctrl + Win`   |
| 取消当前请求 | `Escape`       |
| 停止语音播放 | 再次按下录音键 |
| 显示主窗口   | 托盘菜单       |

`Ctrl + Win` 采用按住说话：两个按键均按下时开始录音，任一按键释放时提交录音。快捷键必须可配置。若与系统或其他应用冲突，应提示用户重新设置，而不是静默失效。若 Tauri 全局快捷键插件不支持仅由修饰键组成的组合，Windows Rust 层应监听该组合的按下与释放状态，上层事件接口保持不变。

### 4.3 注入模式

客户端提供三种模式：

| 模式     | 行为                                        |
| -------- | ------------------------------------------- |
| 听写模式 | 将 ASR 文本注入当前光标位置，不调用 LLM/TTS |
| 助手模式 | 将语音交给 LLM，显示并播放回复              |
| 混合模式 | 显示 ASR 和回复，由用户选择是否直接注入     |

第一阶段默认使用“听写模式”，允许用户切换为助手或混合模式。听写模式默认在识别完成后自动注入；助手和混合模式默认不自动注入，用户可以在设置中分别修改。

### 5.1 职责边界

Rust 层负责必须接触桌面系统能力的部分，不承担音频 DSP 和业务状态管理。Vue 层负责录音数据处理、WebSocket 协议、播放和 UI。服务端负责 VAD 的最终判断、模型推理与音频生成。

客户端可以使用简单的能量门限减少静音数据，但服务端 VAD 是语音起止判断的权威来源。这样可以避免不同设备和浏览器音频实现造成行为不一致。

### 5.2 可替换边界

后续进入原生音频 token 阶段时：

- 保留全局快捷键、权限、录音和播放模块。
- 保留 WebSocket 连接与事件分发框架。
- 将服务端 `ASR → LLM → TTS` pipeline 替换为音频 tokenizer、Multimodal LLM 和 audio decoder。
- 通过协议版本或 capability 协商决定使用 `cascade` 或 `native_audio` pipeline。

### 6.1 录音模块

职责：

- 请求麦克风权限。
- 获取系统默认输入设备。
- 采集单声道浮点音频。
- 重采样到 16 kHz。
- 转换为 little-endian PCM16。
- 每 20 ms 形成一个音频帧。
- 计算 RMS 音量用于 UI。
- 将音频帧交给 WebSocket 发送队列。
- 达到有效录音上限时自动提交；有效上限取本地配置与 `server.hello.limits.max_recording_ms` 的较小值。

统一音频格式：

| 字段              | 值                         |
| ----------------- | -------------------------- |
| sample rate       | 16,000 Hz                  |
| channels          | 1                          |
| sample format     | signed PCM16 little-endian |
| frame duration    | 20 ms                      |
| samples per frame | 320                        |
| bytes per frame   | 640                        |

使用 `AudioWorklet` 采集音频，不使用已经废弃且容易阻塞主线程的 `ScriptProcessorNode`。浏览器实际采样率可能是 44.1 kHz 或 48 kHz，因此必须显式重采样，不能修改元数据伪装成 16 kHz。

录音时应维护单调递增的帧序号。发送队列超过阈值时，应终止当前请求并报告 `audio_backpressure`，不能无限缓存导致内存增长和数秒延迟。

### 6.2 WebSocket 模块

职责：

- 建立和维护一条长连接。
- 完成协议版本和能力协商。
- 发送控制消息与二进制 PCM。
- 接收流式文本、状态、错误和 TTS 音频。
- 管理心跳、超时、重连和取消。
- 将网络事件转换为类型安全的领域事件。

重连策略：

1. 首次失败后等待 500 ms。
2. 后续使用指数退避：1 s、2 s、4 s、8 s。
3. 最大退避时间 15 s。
4. 窗口重新获得焦点或用户点击“重试”时立即重连。
5. 正在进行的请求断线后直接标记失败，不自动重放录音，避免重复提交隐私数据。

### 6.3 会话状态机

客户端使用显式状态机管理交互：

```text
DISCONNECTED
    │ 连接成功
    ▼
IDLE
    │ 按下快捷键
    ▼
RECORDING
    │ 松开快捷键
    ▼
FINALIZING
    │
    ├─ ASR 完成，dictation ─→ INJECTING（启用自动注入时）─→ IDLE
    │
    └─ ASR 完成，assistant ─→ THINKING
                                  │ 首个 LLM token
                                  ▼
                              RESPONDING
                                  ├─ 未请求音频，文本完成 ─→ IDLE
                                  └─ output.audio.start ─→ PLAYING
                                                               │ 播放和文本生成完成
                                                               ▼
                                                              IDLE
```

任意工作状态收到取消操作后进入 `CANCELLING`，收到服务端确认或本地超时后回到 `IDLE`。不可恢复错误进入 `ERROR`，但用户点击重试后必须能回到 `DISCONNECTED` 或 `IDLE`。

客户端 UI 的混合模式在协议层使用 `assistant`。听写模式使用 `dictation`，不得进入 LLM 或 TTS 状态。

状态转换只能由统一的 session store 执行。组件只能派发事件，不能分别维护“是否录音”“是否播放”“是否请求中”等互相矛盾的布尔变量。

### 6.4 流式播放模块

职责：

- 接收服务端音频分片。
- 按 `request_id` 和 `sequence` 排序。
- 维护 80–160 ms 的启动缓冲。
- 连续调度音频，避免分片边界爆音。
- 支持立即停止并清空缓冲。
- 上报首包时间、首播时间、欠载次数和播放完成时间。

第一阶段推荐服务端返回 PCM16，以减少客户端解码差异。带宽成为问题后再协商 Opus。每次 TTS 流开始前，服务端必须发送包含采样率、声道数和格式的 `output.audio.start`，客户端不能硬编码输出格式。

播放队列不得跨请求复用。开始新请求或收到 `cancelled` 时，必须停止当前音源、清空 jitter buffer，并丢弃旧 `request_id` 的迟到分片。

### 6.5 文本注入模块

第一阶段不使用剪贴板。Windows 端通过 Win32 `SendInput` 和 `KEYEVENTF_UNICODE` 直接向当前前台窗口发送 Unicode 键盘输入。

注入流程：

1. 用户触发录音时不锁定注入目标，录音期间的焦点变化不触发额外确认。
2. 悬浮窗使用不激活模式显示，尽量不抢占目标应用焦点。
3. 生成结果后确认录音快捷键及其修饰键均已释放。
4. 注入前获取当前前台窗口，将其作为本次注入目标。
5. 将文本转换为 UTF-16 code units。
6. 对每个 UTF-16 code unit 构造一次 Unicode key-down 和 key-up `INPUT`。
7. 调用 `SendInput` 分批发送，并校验实际成功写入的事件数量。
8. 注入完成后向前端返回成功数量、总字符数、耗时和稳定错误码。

换行统一转换为 Windows 输入事件：

- `\r\n` 和单独的 `\n` 先规范化。
- 换行使用 `VK_RETURN` 的 key-down/key-up，不依赖目标应用处理 Unicode `U+000A`。
- UTF-16 代理对按原顺序发送，以支持 emoji 和其他补充平面字符。

Rust 层定义平台无关接口：

```rust
pub trait TextInjector: Send + Sync {
    fn capture_target(&self) -> Result<TargetWindow, InjectError>;
    fn inject(&self, target: &TargetWindow, text: &str) -> Result<InjectReport, InjectError>;
}
```

第一阶段只提供 `WindowsTextInjector`。后续增加 macOS/Linux 时实现同一 trait，上层 Tauri command、Vue 状态机和 UI 不需要修改。

Windows 实现要求：

- 使用 `windows` crate 调用 Win32 API，不引入跨平台模拟键盘库。
- 不读取、不覆盖也不恢复系统剪贴板。
- 单次注入在 Rust 层串行执行，禁止两个请求同时发送输入事件。
- 注入前检查文本长度；上限可配置，第一阶段默认 8,000 个 Unicode code points，禁止设置为无限制。
- 较长文本分批发送，建议每批不超过 256 个 `INPUT`，批间让出执行权，避免目标程序消息队列阻塞。
- 若当前目标窗口已关闭或 `SendInput` 返回数量不足，立即停止后续输入并返回部分成功报告。
- 受 Windows UIPI 限制，普通权限进程不能向高完整性级别窗口可靠注入；客户端不得为了绕过限制而自动申请管理员权限。
- 某些终端、游戏、远程桌面、沙箱或自行处理 Raw Input 的应用可能忽略合成输入，应作为“不支持目标”明确提示。
- 听写模式的自动注入默认开启；助手和混合模式的自动注入默认关闭。用户可以按模式修改设置。

注入失败时，文本必须继续保留在悬浮窗或主窗口中，并显示失败原因与“重新注入”操作。第一阶段不以剪贴板作为失败降级路径。

### 6.6 窗口与托盘

至少提供两个界面：

- 主窗口：服务地址、快捷键、模式、音频设备和诊断信息。
- 悬浮窗：录音音量、当前状态、ASR 文本、回复文本、取消按钮。

悬浮窗以不激活、置顶且不出现在任务栏中的独立窗口实现。设置页提供悬浮窗显示开关，以及“底部左侧 / 底部居中 / 底部右侧”三种位置；默认显示并位于底部居中。位置相对于当前前台应用所在显示器的可用工作区计算并持久化。任务完成后保留最终状态约 2 秒，然后自动隐藏。

关闭主窗口默认只隐藏到托盘，不退出后台进程。托盘菜单提供：

- 开始/停止录音。
- 打开主窗口。
- 连接状态。
- 设置。
- 退出应用。

## 7. Rust 层设计

### 7.1 Tauri Commands

建议暴露以下命令：

| 命令                         | 作用                                                     |
| ---------------------------- | -------------------------------------------------------- |
| `get_permission_status`      | 查询 Windows 麦克风权限                                  |
| `open_permission_settings`   | 打开对应系统设置页                                       |
| `register_record_shortcut`   | 注册或更新录音快捷键                                     |
| `unregister_record_shortcut` | 注销快捷键                                               |
| `inject_text`                | 获取当前前台窗口并使用 `SendInput` 直接注入 Unicode 文本 |
| `show_overlay`               | 定位并显示悬浮窗                                         |
| `hide_overlay`               | 隐藏悬浮窗                                               |
| `set_overlay_position`       | 更新并立即应用悬浮窗的底部位置                           |
| `get_app_info`               | 返回版本、平台和构建信息                                 |

所有命令返回统一结果：

```ts
type CommandResult<T> =
  | { ok: true; data: T }
  | {
      ok: false;
      error: {
        code: string;
        message: string;
        recoverable: boolean;
      };
    };
```

Rust 错误必须映射为稳定的错误码，不能把平台库的原始错误字符串直接作为前端业务判断条件。

目标窗口句柄只保存在 Rust 调用期间，不暴露给 Web 前端。`inject_text` 只能使用 Rust 在注入前读取到的当前前台窗口，前端不能指定任意进程窗口。

### 7.2 Tauri Events

Rust 向前端发送：

| 事件                         | 数据           |
| ---------------------------- | -------------- |
| `shortcut://record-pressed`  | 快捷键和时间戳 |
| `shortcut://record-released` | 快捷键和时间戳 |
| `shortcut://cancel`          | 时间戳         |
| `permission://changed`       | 当前权限状态   |
| `tray://action`              | 托盘操作名称   |

事件监听器在组件卸载或应用重载时必须注销，避免一次快捷键触发多次录音。

### 7.3 建议依赖

具体版本应在实现时结合 Tauri 2 当前兼容性锁定：

- Tauri global shortcut 插件。
- Tauri store 插件，用于持久化非敏感设置。
- Tauri log 插件。
- `windows` crate，用于 `SendInput`、前台窗口和进程完整性级别相关 Win32 API。
- `thiserror`，用于 Rust 错误类型。
- `tracing` 或插件提供的日志接口。

新增插件时必须同步更新 capability，遵循最小权限原则。

`windows` crate 只启用实际使用的 feature，至少包括：

- `Win32_UI_Input_KeyboardAndMouse`
- `Win32_UI_WindowsAndMessaging`
- `Win32_System_Threading`

## 8. 后端对接边界

客户端第一阶段只依赖服务端提供稳定的 WebSocket 行为，不负责服务端内部的模型选型、推理 pipeline、GPU 调度、部署或性能优化。

当时的正式接口以现已删除的 `WS_PROTOCOL.md` 为准。客户端需要关注的历史对接内容只有：

- 建连、协议版本与 capability 协商。
- 读取 ASR、LLM、TTS 和下行音频候选，并随请求提交用户选择。
- 发起请求、上传二进制 PCM 音频和提交输入。
- 接收 ASR 临时/最终文本。
- 接收 LLM 增量文本。
- 接收带序号的流式 TTS 音频。
- 取消请求、心跳、超时、断线和重连。
- 按稳定错误码更新客户端状态并向用户提供恢复操作。

服务端必须向客户端保证：

- 同一 request ID 的消息状态和顺序符合协议。
- 所有成功、失败或取消请求都有明确终态。
- TTS 失败时尽可能保留文本结果。
- 不要求客户端理解具体模型、tokenizer 或后端框架。
- 模型替换不会无必要地改变客户端协议。

联调时使用 mock WebSocket 服务先验证客户端状态机和协议解析，再接入真实推理服务。后端当时需通过已删除的 `WS_PROTOCOL.md` 中的服务端兼容性检查表和联调验收用例。

## 9. 数据与设置

### 9.1 本地设置

第一阶段持久化：

- 服务端 WebSocket 地址。
- 录音快捷键。
- 工作模式。
- ASR、LLM、TTS 候选 ID 和下行音频候选 ID。
- 输入设备 ID。
- 输出设备 ID。
- 自动注入开关。
- 单次自动注入字符上限。
- 单次录音最大时长。
- TTS 开关、音色名称和音量。
- 界面语言。
- 是否允许匿名性能指标。

不得以明文保存：

- 云端 API Key。
- 认证 token。
- 原始录音。
- 完整对话记录。

调试阶段默认连接本机 mock 服务 `ws://127.0.0.1:8000/v1/voice/ws`；发布环境连接用户配置的远程 `wss://` 服务。第一阶段客户端不实现应用层鉴权，也不保存 API Key 或认证 token。

### 9.2 会话历史

第一阶段会话历史只保存在内存中，默认最多保留最近 10 轮，并限制总字符数或 token 数。应用退出后不保存完整对话。

后续若增加本地历史记录，需要提供清理、导出和禁用功能，并明确数据位置。

## 10. 安全与隐私

- 第一次录音前解释为什么需要麦克风权限。
- 第一次自动注入前说明应用将通过 Windows 合成键盘事件向当前窗口输入文本。
- 录音状态必须有持续可见的视觉反馈。
- 所有活动请求必须允许用户一键取消。
- 本地服务默认绑定 loopback，不能默认监听 `0.0.0.0`。
- 发布环境只允许连接远程 `wss://` 服务并正常校验证书；第一阶段客户端不发送鉴权凭据。
- 日志不记录 PCM、完整识别文本、完整回复或密钥。
- 诊断日志中的文本只记录长度、语言和哈希等非内容信息。
- capability 只开放应用实际使用的 Tauri 命令和窗口权限。

## 11. 日志与可观测性

每个请求至少记录以下时间点：

| 字段                   | 含义               |
| ---------------------- | ------------------ |
| `record_started_at`    | 用户开始录音       |
| `record_committed_at`  | 用户结束录音       |
| `asr_first_partial_at` | 首个 ASR partial   |
| `asr_final_at`         | ASR 最终结果       |
| `llm_first_token_at`   | LLM 首 token       |
| `tts_first_chunk_at`   | 收到首个 TTS 分片  |
| `playback_started_at`  | 客户端实际开始播放 |
| `request_done_at`      | 请求完全结束       |

由此计算：

- ASR latency。
- LLM TTFT。
- TTS first-chunk latency。
- TTF-Audio。
- 总请求时间。
- 网络发送队列峰值。
- 播放缓冲欠载次数。

日志字段包括 `request_id`、应用版本、协议版本、pipeline、平台和错误码。客户端与服务端使用同一个 `request_id` 关联问题。

## 12. 性能预算

目标预算：

| 阶段                     |       预算 |
| ------------------------ | ---------: |
| 录音结束、尾点处理和提交 | 100–200 ms |
| ASR final                | 300–600 ms |
| LLM 首 token             | 300–700 ms |
| 首句积累与 TTS 首分片    | 500–900 ms |
| 网络与客户端播放缓冲     | 100–200 ms |
| 总 TTF-Audio             |  1.3–2.6 s |

如果超过 3 秒，按以下顺序定位：

1. 确认 `input.commit` 是否及时发送。
2. 区分 ASR、LLM、TTS 和客户端播放缓冲耗时。
3. 检查是否等待完整 LLM 回复后才启动 TTS。
4. 检查 TTS 分句是否过长。
5. 检查 WebSocket 发送队列和音频播放欠载。
6. 检查模型冷启动、连接冷启动和 GPU 资源争用。

## 13. 开发里程碑

### M0：工程基线

交付：

- 清理默认 Tauri 示例页和 `greet` 命令。
- 建立模块目录和统一错误类型。
- 配置格式化、静态检查和基础 CI。
- 主窗口能展示应用版本与服务连接状态。

验收：

- `npm run build` 通过。
- `cargo check` 通过。
- Windows 目标平台可启动。

### M1：本地录音

交付：

- 麦克风权限请求。
- AudioWorklet 音频采集。
- 16 kHz PCM16 重采样。
- 音量显示和录音时长。
- 本地录音开始、停止、取消。

验收：

- 录制 10 秒音频，帧数和时长误差 < 1%。
- PCM 文件经离线检查可正常播放且语速正常。
- 连续录音 20 次无残留 MediaStream。

### M2：WebSocket 与 ASR

交付：

- 协议握手、心跳和重连。
- PCM 二进制流上传。
- ASR partial/final 展示。
- 连接和 ASR 错误处理。

验收：

- 本地服务下连续识别 20 条短句无状态卡死。
- 网络中断后能恢复到可重试状态。
- 旧请求的迟到消息不会污染新请求。

### M3：LLM 与文本注入

交付：

- LLM 文本流展示。
- 听写、助手和混合模式。
- 全局快捷键。
- 基于 `SendInput` 的 Unicode 文本注入和失败处理。

验收：

- 能向常见 Windows 编辑器和浏览器文本框直接注入中文、英文、标点、换行和 emoji。
- 注入全程不读取或修改剪贴板。
- 注入部分成功或失败时文本不会丢失，并能重新注入。
- 对高权限窗口等不支持目标返回明确错误。
- 快捷键冲突有明确反馈。

### M4：TTS 流式播放

交付：

- `output.audio.start`、二进制音频和 `output.audio.done` 处理。
- jitter buffer。
- 边接收边播放。
- 停止和语音打断。
- 播放延迟指标。

验收：

- 不等待完整 TTS 即开始播放。
- 连续分片无明显爆音。
- 取消后 200 ms 内停止播放。
- TTS 失败不影响文本结果。

### M5：产品化与联调

交付：

- 托盘、悬浮窗和设置页。
- 权限引导。
- 结构化日志与延迟面板。
- 安装包和演示脚本。
- 协议文档冻结为 `1.0`。

验收：

- 完成端到端验收用例。
- TTF-Audio P50 < 2.5 秒，P95 < 3 秒。
- 连续运行 30 分钟无崩溃和显著内存增长。

## 14. 测试方案

### 14.1 单元测试

- 重采样输出长度和频率正确。
- Float32 到 PCM16 的裁剪和端序正确。
- 协议 JSON 序列化和未知字段兼容。
- ASR revision 覆盖逻辑。
- LLM sequence 去重和排序。
- 状态机合法/非法转换。
- jitter buffer 清理和请求隔离。
- Rust 错误到前端错误码的映射。

### 14.2 集成测试

实现一个不依赖 GPU 的 mock WebSocket 服务：

- 接收 PCM 后返回固定 ASR 文本。
- 按指定间隔返回 LLM delta。
- 生成简单正弦波作为 TTS PCM。
- 在 `server.hello.inference_options` 中返回可选择的 ASR、LLM、TTS 和下行音频候选。
- 可注入超时、断线、乱序、重复和错误消息。

集成测试覆盖：

- 正常助手请求。
- 听写模式。
- 录音中取消。
- LLM 生成中取消。
- 播放中被新请求打断。
- 服务端断线和重连。
- 服务端候选列表正常展示、选择并随 `request.start` 提交。
- 已保存的候选 ID 失效时回退到服务端默认项并提示用户。

- TTS 失败后的文本降级。

## 15. 完成定义

第一阶段只有在以下条件全部满足时才算完成：

- 用户能够通过全局快捷键完成一次无需操作主窗口的语音请求。
- ASR、LLM 和 TTS 的级联链路端到端可用。
- 文本能在已验证的 Windows 应用中通过 `SendInput` 注入，且不经过剪贴板。
- 语音能够流式播放并被用户立即打断。
- 所有工作状态均有明确 UI，错误后可以恢复。
- 协议包含版本、请求 ID、取消和稳定错误码。
- 客户端和服务端都能输出可关联的分阶段延迟。
- 自动测试覆盖状态机、协议和关键音频工具函数。
- Windows 完成一轮手工验收。
- 本地基准环境中 TTF-Audio P95 小于 3 秒。
- 不依赖保存用户原始录音或完整对话才能运行。

## 16. 风险与应对

| 风险                              | 影响                   | 应对                                                                 |
| --------------------------------- | ---------------------- | -------------------------------------------------------------------- |
| 浏览器采样率不固定                | ASR 速度或准确率异常   | AudioWorklet 中显式重采样并测试                                      |
| TTS 等待完整回复                  | TTF-Audio 超标         | LLM 增量分句后立即合成                                               |
| 音频分片播放有间隙                | 体验不自然             | jitter buffer 和连续 AudioContext 调度                               |
| 全局快捷键冲突                    | 无法开始录音           | 可配置快捷键和冲突提示                                               |
| Windows UIPI 阻止跨完整性级别输入 | 无法向管理员窗口注入   | 不自动提权，返回明确的不支持错误                                     |
| 目标应用忽略 `SendInput`          | 文本注入失败或部分成功 | 校验返回数量、保留文本并允许重新注入                                 |
| 注入时焦点发生变化                | 文本进入当前新窗口     | 第一阶段不做特殊确认；注入时以当前前台窗口为准，并在设置中说明该行为 |
| WebSocket 断线产生脏状态          | 无法继续请求           | 显式状态机、请求 ID 和超时清理                                       |
| 服务端模型接口频繁变化            | 客户端重复修改         | 冻结协议，模型变化封装在服务端                                       |
| 录音或文本进入日志                | 隐私风险               | 默认只记录指标和错误码                                               |

## 17. 已冻结的客户端决策

以下内容构成 Phase 1 的历史客户端实现基线；对应协议已由 Voice API v2 取代。

| 决策项     | 冻结结论                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 目标平台   | 仅实现和验收 Windows                                                                                        |
| 录音快捷键 | 默认 `Ctrl + Win`，采用按住说话；支持用户配置                                                               |
| 工作模式   | 默认听写模式，可切换助手或混合模式                                                                          |
| 服务位置   | 调试连接本机 mock；发布连接远程服务器                                                                       |
| 服务地址   | 调试默认 `ws://127.0.0.1:8000/v1/voice/ws`；发布必须使用用户配置的 `wss://` 地址                            |
| 推理候选   | 服务端在握手时提供 ASR、LLM、TTS 候选 ID、名称和说明，客户端展示并保存用户选择                              |
| 音频格式   | 上行固定为 16 kHz、单声道 PCM16LE；下行采样率在服务端候选范围内可配置，实际格式以 `output.audio.start` 为准 |
| 鉴权       | Phase 1 客户端不实现应用层鉴权，不发送或保存鉴权凭据                                                        |
| 自动注入   | 听写模式默认开启；助手和混合模式默认关闭；均可配置                                                          |
| 焦点变化   | 不弹窗、不恢复旧窗口；注入时以当前前台窗口为目标                                                            |
| 注入长度   | 可配置，默认上限 8,000 个 Unicode code points；不得配置为无限制                                             |
| 录音时长   | 可配置，默认上限 60 秒，同时不得超过 `server.hello.limits.max_recording_ms`                                 |

模型参数量、服务端模型选型、推理部署和性能优化不属于客户端 Phase 1 的冻结范围。客户端只依赖协议声明的 capability、候选项和资源限制。
